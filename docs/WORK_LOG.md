# 작업 기록

표기: **확인**은 직접 실행하거나 로그로 확인한 것, **추정**은 근거는 있지만 확인하지 못한 것이에요.

## 0. 배경

EasyBlue(ZARAM)는 USB 동글이에요. PC 키보드·마우스 입력을 블루투스로 폰에 보내 줘요.
제조사는 Windows·Mac용 프로그램만 내놨고, Ubuntu용은 없어요.

## 1. 6월 29~30일: Ubuntu 포팅 시도 (이전 세션)

- Wine으로 Windows 앱을 띄워 봤지만 동글을 인식하지 못했어요.
- 이전 Agent가 동글과 직접 통신을 시도했어요. 그러다 6/30 아침부터 동글이 정상 모드(`1d54:b002`)가 아니라 **`1d54:f300` "ZVMP300 HID-UMS" 부트 모드로만 잡혀서** 쓸 수 없게 됐어요(확인: 프롬프트 기록, udev 규칙 날짜).
- 같은 날 PC 자체 블루투스로 폰을 조작하는 방식(`legacy/bt_hid.py`)을 시도했어요. 폰의 "텍스트 입력"이 계속 꺼지는 문제로 중단했어요.

## 2. 10월 15일: EasyBlue 동글 조사

- 동글은 USB에서 `1d54:f300`으로 인식되고, 2TB짜리 가짜 디스크(`0xFFFFFFFF` 섹터)를 보여 줘요(확인).
- 공식 업데이터 `EasyBlue_Update.exe`를 Windows에서 관리자 권한으로 실행해도 "장치를 찾을 수 없음"이었어요(확인: 사용자 테스트).
- Ghidra로 공식 Windows·Mac 업데이터를 디컴파일했어요. **두 업데이터 모두 정상 모드(`b001`/`b002`)만 다루고, `f300` 모드를 처리하는 코드는 없어요**(확인).
- 원인 (추정, 유력): 정상 모드의 `EB02` 명령 묶음이 내장 플래시를 다뤄요. 이전 작업 중 플래시가 지워졌고, 재부팅하면서 칩 내장 부트 모드로 떨어진 것으로 보여요.
- 결론: 공식 도구로는 복구할 수 없어요(확인). 하드웨어 수리는 사용자가 불가능하다고 판단했어요. 이 방향은 여기서 중단했어요.
- 동글에는 읽기·조회 명령만 보냈어요. 상태는 조사 전과 같아요.

## 3. 10월 15일: PC 블루투스 방식 다시 시도

**결정:** 동글 없이 PC 블루투스를 HID 장치로 쓰기로 했어요.
- scrcpy는 사용자가 느리다고 했고, 무선 ADB를 계속 켜 두는 것도 원하지 않았어요.

`legacy/bt_hid.py`를 살리면서 찾은 문제들이에요.

| 증상 | 원인 | 해결 |
|---|---|---|
| 장치 종류 설정이 적용 안 됨 | 스크립트가 `hci1`을 지정했는데, 실제 어댑터는 `hci0` (확인) | `hci0`으로 수정 |
| 폰 페어링 "연결할 수 없음" | 페어링 요청을 받아 줄 에이전트가 없음 (추정) | 자동 수락 에이전트 실행 |
| "통화 및 오디오를 위해 연결됨"만 됨 | PC가 오디오 서비스를 내보내고 있었고, 키보드 쪽에서 먼저 연결을 걸지 않음 | PC가 폰에 HID 연결을 거는 기능 추가 |
| 연결 직후 끊김, "텍스트 입력" 자동 Off | **`hid.xml`의 HID 속성 번호가 한 칸씩 밀려 있었음.** 디스크립터가 `0x0206`이 아니라 `0x0205`에 있었어요. 폰 로그: `bta_hh_sdp_cmpl ... BTA_HH_ERR_SDP` (확인, 무선 ADB logcat) | 표준 번호로 `hid.xml` 재작성 → **동작 확인** |
| 한/영 전환 안 됨 | kr104 배열에서 한/영 키 = 오른쪽 Alt(100). 전달 단축키의 일부로만 처리됨 (확인) | 한/영 키를 단독으로 눌렀다 떼면 폰에 Shift+Space 전송 |
| 전달 중에도 PC에 입력이 들어감 | 입력 장치를 독점하지 않았음 | 전달 켜짐 동안 evdev grab, 연결이 끊기면 자동 해제 |

사용자가 실제 폰에서 키보드, 마우스, 한/영 전환, PC 입력 차단이 모두 되는 걸 확인했어요.

## 4. 10월 15일: 프로그램화 (`app/`)

사용자 요구사항이에요.
1. 우측 상단 트레이에 늘 떠 있어야 해요.
2. 설정 창에 버튼 세 개가 있어야 해요: 신규 장비 페어링, 기존 장비 페어링 삭제, relay 단축키 설정.
3. 연결 상태와 기기 정보를 보여 줘야 해요.
4. 페어링할 때 통화·오디오는 빼고 "텍스트 입력"으로만 연결돼야 해요.

**설계**
- 구조는 root 데몬 `bthidd`(systemd)와 사용자 트레이 `bthid-tray`(AyatanaAppIndicator)로 나눴어요. 둘은 Unix 소켓 `/run/bthid/ctl.sock`(JSON)으로 통신해요.
- 통화·오디오를 빼는 방법을 실험했어요(확인).
  - WirePlumber를 멈추면 통화(HFP) 항목은 사라져요.
  - 오디오(A2DP) 항목은 bluetoothd가 직접 등록해서 남아요.
  - 그래서 페어링하는 동안만 bluetoothd를 `--noplugin=input,a2dp,avrcp`로 다시 띄워요. 폰은 페어링할 때 이 PC를 키보드로만 기록해요.
- 안전장치를 두 겹으로 뒀어요.
  - 페어링한 폰은 "신뢰하지 않음"으로 둬요. 에이전트는 이 폰의 HID 외 연결을 거절해요(`AuthorizeService`).
  - 폰이 오디오 프로필로 연결되면 끊어요(`DisconnectProfile`).

**검증** (조직 원칙: 구현자 ≠ 검증자)
- 1차 독립 검증에서 치명 1건, 주요 8건, 경미 10건이 나왔어요.
  - 치명 1건: 입력 스레드가 예외로 죽으면 PC 입력이 잠긴 채로 남을 수 있었어요.
  - 커버리지가 52%로 기준(80%)에 못 미쳤어요.
- 모두 고쳤어요. 주요 수정 내용이에요.
  - 입력 스레드 감시와 자동 재시작
  - 단축키 자동 반복 무시
  - 전달은 단축키를 뗄 때 켜지게 변경
  - 마우스 이동을 프레임 단위로 묶어서 전송
  - 페어링 상태 처리 타임아웃
  - 연결 수신 루프 재시작 버그 수정
  - 제어 소켓 보호, 트레이 응답성 개선
- 2차 검증에서 이전 지적은 모두 해결로 확인됐어요(1차 판정 철회). 경미 4건이 새로 나왔어요.
- 그 4건을 고쳤고, 3차 검증에서 해결을 확인했어요. **테스트 67개 통과, 커버리지 데몬 91% / 트레이 97%.**

**실기기 결과 (16:08 로그, 확인)**
- `pairing: bonded with AA:BB:CC:11:22:33`: 페어링 성공
- `AuthorizeService ... 0000111e (Handsfree) -> REJECT`: 통화 연결 거절
- `HID connected to ... (PC-initiated)`, `relay ON` / `relay OFF`: 키보드 연결과 전달 동작

## 5. 남은 일

- 폰 화면에서 이 PC의 "텍스트 입력"만 켜져 있는지 직접 확인하기(미확인)
- 폰은 페어링 뒤에도 오디오 연결을 계속 시도하고, PC가 매번 끊어요. 로그에 `audio profile disconnected`가 반복되는 이유예요. 동작에는 문제가 없지만 로그가 많아요.
- 알려진 제약
  - 페어링 창 2분 동안은 근처의 아무 기기나 먼저 페어링하면 대상 폰이 돼요.
  - 전달이 켜진 동안에는 트레이 메뉴를 마우스로 누를 수 없어요. 비상시에는 단축키를 쓰거나, SSH로 접속해 `systemctl stop bthidd`를 실행해요.
